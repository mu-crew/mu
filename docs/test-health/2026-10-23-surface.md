### MERGE / DELETE proposals and refutations

I propose no MERGE and no DELETE, so step 3 (refuter) had nothing to
check. I considered the candidates below and refuted each myself, and
they stay KEEP:

- **`wait-arming-mux` "delivered" vs "delivery-UNKNOWN" (1.6 s each).**
  Merging them into one test loses the UNKNOWN branch's own assertion: it
  arms the task only, not the agent. Two outcomes need two tests.
- **The four `sync-contract` permutation sets (≈ 11 s together).** Each
  is a different refuter's op sequence (restore, fold-in, del-between-puts,
  first-life leak). Deleting any one leaves a named past bug without a
  guard.
- **`cold-guess` golden/bad/no-op per intent (5 intents).** Each intent's
  judge is a different piece of code. Keeping one would leave four judges
  unproven, and the eval's correctness rests on them.
- **The `notes-view` property next to the explicit boundary tests.** The
  explicit tests pin known edges, and the property finds unknown ones (the
  footer-decides sets). Not duplicates.

## Where the fast tier's time goes

I added temporary instrumentation to `openDb` (reverted, not committed)
and ran the fast gate once with it: **6034 fresh-file `openDb` calls cost
156 s, which is 48% of the 325 s of summed file time.** 930 reopens of an
existing file cost 2.7 s. A fresh open runs the whole v13 DDL plus the
capture triggers, about 44 ms on an idle core. Copying a pre-built file
and reopening it takes about 5.5 ms (measured in a probe test, not
committed).

This is the one lever that could bring the fast gate back near budget
without losing a case. One shared test helper would do it: a lazily built
template DB per fork, copied per test. It has to keep a distinct
`machine_identity` per test (sync tests compare machine ids), so a copy
must re-key that row. That is a harness change across about 200 files
(524 `openDb(` call sites in `test/`), not a 2 h test-only fix, so it is a
follow-up. The wire-matrix change above is the same idea applied to a
single file.

## Remaining bottleneck and follow-ups

1. **Fresh `openDb` in tests: 156 s of 325 s fast-tier file time.** This
   needs a shared template-DB helper (`test/_db.ts`) that copies a built
   v13 file per test and re-keys `machine_identity`. Expected to cut the
   fast tier's summed time by roughly 40%. Untested estimate. A harness
   change with review, not a broad edit.
2. **`cold-guess.integration` 36 s, the largest slow-tier file.** Set
   `MU_SPAWN_LIVENESS_MS=0` in the eval seed path or the test's sandbox env
   (`--no-ctl` sleep panes need no liveness scan). The two seeding intents
   would drop from about 19 s to about 2 s. This is in `tools/eval`, so it
   needs a check that measured eval runs do not depend on the window.
   *Kept on purpose (R6 review, rr_r6_p3_batch):* the liveness window is part
   of what a cold-guess run measures, so it stays until that check is done.
3. **Serial integration under load: 8m31s.** The 85 `*.integration` files
   take 187 to 199 s of summed time, against ~64 s at the kernel milestone.
   The kernel report's Layer 3 suggestion still applies: a private tmux
   socket per file would let the tmux-free integration files run in
   parallel. This would be a harness change. `--maxWorkers=2` already
   shows the effect on this host (4m36s vs 8m31s), with no failures.
4. **The fast budget of 30 s was measured on an idle host with half the
   tests.** After 1 to 3 the budget should be re-measured on an idle host
   before AGENTS.md's "Today" column is changed. This report does not
   change AGENTS.md: its numbers were taken at load 4 to 10 and are not
   comparable.
