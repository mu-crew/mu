## Goal

opencode orchestrates and works in a mu crew as well as the other blessed
harnesses. Its server API gives mu exact admission, steer and interrupt,
which `hooks` lacks; mu uses them without claiming more than they prove.

## How opencode 2 differs from the other harnesses

Claude Code, Codex, cursor-agent and Muse Code are each **one process in
one pane**. That process talks to the model and runs the tools as its own
children, so tools inherit the pane's env (`MU_*`, `TMUX_PANE`) and sit
under the pane in the process tree. mu drives them through the terminal:
it pastes into the input box, presses keys, and learns what happened from
the shell hooks they fire (EH-D3, D4). Delivery is never exact; mu pastes,
watches the run count, and never resends.

opencode 2 is **a client and a server**:

```text
pane:  opencode (TUI) ──HTTP──► opencode serve --service   (one per machine, detached)
pane:  opencode (TUI) ──HTTP──┘   ├─ talks to the model
                                  ├─ runs every tool (shell, edits)
                                  └─ stores sessions in SQLite
```

| | the other four | opencode 2 |
|---|---|---|
| where the agent runs | the pane's process | a shared background server; the TUI only draws and sends input |
| where tools run | children of the pane's process | children of the server, outside the pane's process tree |
| tool env | the pane's env | the env the TUI uploads for its session, held in the server's memory; any TUI showing the session replaces it |
| who owns the runtime | each pane | whoever started the server first (maybe a sandboxed agent); a TUI of another version restarts it for everyone |
| how mu delivers | tmux paste, keys | an HTTP API: create a session with a chosen id, prompt with a message id, steer, interrupt, answer dialogs |
| how mu learns state | shell hooks writing murmur's inbox | no shell hooks: TUI plugins (in the pane), server plugins (in the server), an event stream and a durable per-session log |
| sessions | the CLI's own JSONL files | SQLite rows rewritten while streaming, exported through the API |
| one agent | one pane | one session; many sessions and many clients (TUI, web, desktop, ACP, `opencode api`) per server |

So opencode 2 is already a session multiplexer of its own: a session is the
agent, and a pane is just one viewer of it. It is not an orchestrator (no
tasks, claims, worktrees, mixed harnesses or remote hosts); that stays
mu's. Two consequences shape everything below:

- **Better delivery than the hook harnesses.** The API gives mu exact
  admission, steer and interrupt, close to pi's control socket.
- **Identity and lifetime are not per pane.** Env, process tree, sandbox
  and restarts all belong to the server, so mu must own the server its
  workers use (O1), or accept the shared one's holes.

A further option, not designed here: **pane-less opencode workers**, driven
purely over the API, with a pane only as an optional viewer
(`opencode --server … --session …`). See H5.

## The central decision: a crew-owned opencode service (O1)

Draft 1 used the user's shared background service. Every high finding about
identity, readiness, skew, sandboxes and restarts traces to that: the shared
service is started by whoever comes first (maybe inside a sandbox), is
restarted by any TUI of another version, keeps each session's env in memory
and lets any TUI that shows a session replace that env
(`tui/src/app.tsx:528-538`, `core/src/session/environment.ts:17-29`,
`client/src/service-probe.ts:22-24`).

So mu runs **its own opencode server per machine**, used only by mu's
opencode agents:

- `opencode serve --hostname 127.0.0.1 --port <p>` (`cli/src/commands/commands.ts:582`),
  with `OPENCODE_DB=<mu state>/opencode/opencode.db` (`cli/src/database-path.ts:6`)
  and `OPENCODE_SERVER_PASSWORD=<mu secret>` (`cli/src/env.ts:11`). One
  managed server per database, as opencode's restart recovery assumes
  (`core/src/session/execution/restart.ts:54-61`). Config, providers and
  auth stay the user's (config dir unchanged).
- **Born outside every sandbox** (EH-D10): mu starts it as a tmux pane or
  `run-shell` job of the tmux server, never as its own child, and refuses
  from inside an agent when it is not running.
- **Pinned:** mu records its pid, start time, port and `opencode --version`
  in `<mu state>/opencode/server.json` (0600). A spawn refuses
  (`OpencodeServerSkewError`) when the CLI on `PATH` differs from the running
  server's version; `mu opencode restart` is the explicit, human step, and
  it refuses while an opencode agent is busy.
- **TUIs attach with `--server <url>`** and the password in their env. With
  `--server`, a TUI uploads no environment (`cli/src/commands/handlers/default.ts:145`),
  and never replaces or restarts the server.
- The user's own service and TUIs are untouched. A human can watch a crew
  session with `opencode --server <url> --session <id>`; that TUI uploads
  nothing either.

Cost: one more long-lived process per machine, and crew sessions live in a
separate DB (museum reads both, O9). **Human decision H1.**

## What opencode 2 offers (facts the design rests on)

- **Session create with a chosen id:** `POST /api/session {id: "ses_…", location:{directory}, model:{providerID,id,variant?}, permissions?, metadata?, title?}`
  returns the existing session for a known id (`core/src/session.ts:288-294`).
  `opencode --session <id>` opens an existing session
  (`cli/src/commands/handlers/default.ts:54-59`).
- **Environment:** `PUT /api/session/{id}/environment` replaces the env local
  shells of that session use (`protocol/src/groups/session.ts:800-813`); no
  GET. Children do not inherit it (`core/src/tool/plugin/subagent.ts:183-212`):
  their shells use the server's own env (`core/src/shell.ts:303-306`).
- **Prompt:** `POST /api/session/{id}/prompt {id:"msg_…", text, delivery:"steer"|"queue"}`
  durably admits to the inbox; a repeat of an id still pending or delivered
  returns the existing item (`core/src/session/inbox.ts:177-190`). Not
  across a cancel or a committed revert (`inbox.ts:378-397`,
  `core/src/session/projector.ts:1131-1160`). A repeat still calls
  `execution.wake` (`core/src/session/session.ts:155-189`).
- **Execution:** one `session.execution.started`, then exactly one of
  `.succeeded`, `.failed {error}`, `.interrupted {reason}`. A steer joins the
  running execution. `POST …/interrupt` returns `{interrupted}`, meaningful
  only on the owning server (`core/src/session/execution.ts:151-166`); with
  one crew server, that is always mu's.
- **Dialogs:** `permission.asked {id, sessionID, …}` and `form.created`
  (the question tool) are ephemeral; the TUI aggregates descendants' dialogs
  onto the root (`tui/src/routes/session/index.tsx:203-223`). Reply:
  `POST /api/session/{sid}/permission/{req}/reply {decision}`, forms through
  `form.reply`.
- **Durable log:** `GET /api/experimental/session/{id}/log?after=<seq>&follow=true`
  replays durable session events from a sequence; `/api/event` is volatile
  (overflow closes it, `server/src/event-feed.ts:47-72`).
- **Server plugins:** `tool.execute.before` (mutable `tool`, `input`,
  carries `sessionID`; `core/src/tool.ts:183-185`), `shell.create.before`
  (mutable env, no session id), `permission.evaluate`,
  `session.experimental.idle` (admitted input runs in the same execution,
  `core/src/session/runner/llm.ts:178-188`), `ctx.session.synthetic`.
- **Text:** `session.text.ended {sessionID, assistantMessageID, ordinal, text}`
  (`schema/src/session-event.ts:420-430`).
- **Process chain:** `opencode` (sh shim, `exec`) → `opencode.exe` (TUI).
  The server and tool shells are not in the pane's chain.
- **TUI:** no `--model`; `--auto` is client-side and only while the session
  route is mounted (`tui/src/routes/session/index.tsx:269-286`); no trust
  prompt. Skills from `~/.config/opencode/skills`, `~/.claude/skills`,
  `~/.agents/skills`. Tool env markers `OPENCODE=1`, `OPENCODE_SESSION_ID`.
- **Sessions:** SQLite (WAL), messages rewritten while streaming;
  `GET /api/experimental/session/{id}/export` returns `{info, messages}` of
  settled messages; `GET /api/session` pages by cursor (default 50).

## Decisions

### O2. The harness row

`opencode` joins `HARNESSES` in mu, murmur and museum. Every matcher and
classifier is updated, not only the tuples: mu `src/hook-chain.ts`
(chain and one-shot), murmur `src/harnesses.ts` (`harnessFromArgv`,
`runMode`), museum `harness_of`. `.exe` joins the stripped suffixes.
Classified: `opencode` / `opencode.exe` with no subcommand (or a directory
argument) is the interactive TUI; `run` is a one-shot; `serve`, `api`,
`session`, `mini`, `service` are never an agent. A one-shot `opencode run`
under any interactive harness is nested (EH-D3).

| Field | opencode |
|---|---|
| default channel | `opencode` (O4) |
| hook config | server plugin `~/.config/opencode/plugins/mu-crew/index.ts` (O5); TUI plugin `~/.config/opencode/plugins/murmur/tui.ts` (O6) |
| events | O6's mapping |
| startupSessionStart | immediate: mu creates the session (O3) |
| fresh | respawn the pane on a new session (O4) |
| interrupt / clear-input key | none: the API |
| can block on stop | yes: `experimental.idle` (O7) |
| marker env | `OPENCODE`, `OPENCODE_SESSION_ID` |
| sessions | crew DB and user DB, through export (O9) |
| trust flag | none |
| model | on create, `provider/model[#variant]` resolved against `GET /api/model` (or the catalog) before the effect |
| auto-approve | the session's `permissions` ruleset on create (O3), not `--auto` |
| skill location | `~/.config/opencode/skills/`; given a copy only while `~/.claude/skills` holds none (it reads that too) |

### O3. Spawn, journaled

The EH-D17 order, with the session made first and every step recoverable:

1. **reserve**: the spawn receipt gains `oc_session` (`ses_<attempt ulid>`,
   derived from the attempt key, so a replay derives the same id) and
   `oc_server` (server.json's instance id). Written before any effect.
2. **create**: `POST /api/session` with that id, `location.directory` (the
   worker's cwd), the resolved model, `metadata.mu = {workstream, agent,
   attempt}` and the permission ruleset: allow everything the user's config
   does not explicitly deny, so a worker meets a dialog only for an explicit
   `ask` rule. Idempotent by id: a replay that finds the session reuses it.
3. **env**: `PUT …/environment` with the worker's env (the anchor's `MU_*`,
   the pane's `TMUX`/`TMUX_PANE` once known; the server's own env minus
   `MU_*` as the base). Synchronous, and repeated after every pane change
   and after every server restart, before any prompt (O8).
4. **pane**: the anchor wrapper (EH-D3) writes the anchor with `cli:
   opencode`, `oc_session`, `oc_server`, and runs
   `opencode --server <url> --session <ses> <cwd>`.
5. **claim**, **sending**: unchanged.
6. **write**: `POST …/prompt {id: msg_<msgId>, text: brief, delivery: queue}`.
   The admission reply is `sent`; no reply is `unknown` and is **never
   resent** (EH-D17). The `msg_` dedupe is a second safety net, not the rule.
7. **sent**, and the receipt pins the brief note.

Readiness is the server, not the TUI: the brief is admitted to the session
whether or not the TUI has drawn, so the first-paste race (EH-D4) is gone.
An orphan (created, never reached `sent`) is deleted by `mu agent close`
and by reconcile when its receipt rolled back.

### O4. The `opencode` channel

A built-in `ChannelImpl` in `src/channels/opencode.ts`, registered beside
`ctl`, `hooks`, `mux`, with its API client in `src/channels/opencode-api.ts`.

**Caps** (`src/channels/types.ts`): `receipt: exact` (admission by inbox
id), `fence: none` (a guarded call is refused, as on `hooks`; dedupe is not a
fence), `steer: yes`, `lastText: yes`, `answer: decision`.

**Runs.** `runs` counts **settled executions** (succeeded, failed or
interrupted) in the agent's current session; `baseline` is
`{session, runs, lastSeq}` read from the durable log. A send is
acknowledged by its own admission and then by `session.inbox.delivered` for
that inbox id, never by a rising count, so a steer that joins a running
execution acks correctly.

| Seam method | opencode |
|---|---|
| send | `prompt {id, text, delivery: queue}`; reply = admitted; delivered = `inbox.delivered` for its id |
| steer | same with `delivery: steer` |
| receipt (`mu agent check`) | inbox item or delivered message with that id, else `not-accepted` only when the durable log since the send's baseline has no admission of it, else `unreachable` |
| interrupt (text) | `interrupt`, await `execution.interrupted` (or settle), then send the replacement text (EH-D4) |
| abort | `interrupt`, await settle; `mu agent close` stays the caller's |
| answer | `mu agent answer <w> once|always|reject` (and `--form <values>`); keys are refused on this channel with a typed error. Targets the oldest pending dialog of the root or its descendants, by request id |
| fresh | create a new session (O3 steps 1–3, new attempt id), then `tmux respawn-pane` the pane with `--session <new>`; the anchor is rewritten; the old session stays readable |
| command | `/compact` → `session.compact {id}`; `/new` → fresh; anything else refused with `ChannelCommandUnsupportedError` |
| settle / last text | O6 |

### O5. One mu-crew server plugin

`mu init` writes `~/.config/opencode/plugins/mu-crew/index.ts`. It loads in
every opencode server but acts only in mu's (it checks an env marker mu sets
on the crew server), so the user's service is untouched.

- **Keep-driving** (O7).
- **Children**: `tool.execute.before` for a session whose root carries
  `metadata.mu` and that is not the root itself runs with no managed
  identity: children are nested agents (EH-D3, EH-D7) and never act as the
  worker. Their shells see the server's env, which has no `MU_*`.
- **muzzle** stays muzzle's own plugin (O10).

### O6. State: the durable log, plus a live hint

- **Authoritative:** mu's channel reads the durable per-session log from the
  stored `lastSeq` (EH-D11's relay pattern): on every channel read and
  watch, it applies the events since the last sequence into murmur through
  `murmur hook mu --by harness`, suppressing duplicates by sequence.
  Dialogs (ephemeral) are re-read from `GET …/permission` and the form list
  on every read, aggregated over descendants, each keeping its request
  type, child session and id. Blocked is recomputed from that set, never
  cleared by one reply.
- **Live hint:** murmur's TUI plugin (`murmur init`) writes inbox events for
  the pane's own session (the anchor's `oc_session`) as they arrive, so
  murmur's UI is current without a mu call. It is advisory: the log wins on
  every read.
- **Mapping:** `execution.started` → `prompt_submitted`; `.succeeded` →
  `turn_stopped`; `.failed` → `turn_failed`; `.interrupted` → `interrupted`
  (confirmed); dialogs → `permission_requested`; `session.deleted` →
  `session_end`. murmur's `run_count` follows settled executions for
  opencode (O4).
- **Last text per execution:** the text of the last `session.text.ended`
  whose `assistantMessageID` belongs to this execution's interval (between
  its `started` and its terminal event in the log). An execution with none
  has no text, never an earlier turn's. CLOSE blocks are read only from
  that.
- A TUI that failed to load the murmur plugin loses only the live hint;
  `murmur doctor` reports it from the plugin list.

### O7. Keep-driving and the close nudge

The mu-crew plugin's `session.experimental.idle` hook, for a root session
with `metadata.mu`, runs
`mu hook stop opencode --session <ses> --server <instance>` (a new,
session-addressed form, parsed and tested; the agent is found by
`oc_session` on its agents row, in the DB the anchor named, with that
agent's `MU_NUDGE` and role) and, on a block answer, admits the reason with
`ctx.session.synthetic`. The answer is one JSON line
(`{decision, reason}`); anything else allows. EH-D7's guards and the
`keep_driving` cap apply. The hook is experimental: if a release drops it,
`mu doctor` says so and opencode agents fall back to the SKILL.md rule
(as Muse does).

### O8. Server lifetime and restarts

- mu checks `server.json` (pid, start time, version) before every effect.
  Gone: the effect fails typed, before touching anything.
- After a server restart, mu re-PUTs every live opencode agent's env before
  any send. Restart recovery may resume an execution before that
  (`restart.ts:249-255`): VERIFY in O0 whether a resumed execution runs
  tools before the PUT; if it does, mu starts the server with recovery
  disabled (if a config allows) or interrupts resumed managed sessions and
  reports them.

### O9. museum

museum gains a **snapshot** source kind beside its append-only ones:

- Discovery per DB (the user's service and mu's server, credentials from
  their registration files): page `GET /api/session` by cursor, all
  projects and children, keeping a high-water mark and a set of failed ids
  to retry; the mark advances only after the snapshots are stored.
- Each changed session (by `time.updated` and a content hash) is exported
  and written atomically to
  `<store>/<machine>/opencode/<project folder>/<ses_id>.json`, replaced,
  never appended: a new replace-mode transfer and include list, not
  `--append-verify`.
- Search and stats learn `.json` snapshots: discovery, reader, a
  normaliser (`user`/`assistant` messages, `text` parts, each `tool` part as
  a call and a result), cache invalidation on replace. Filter drops
  `native.*.reasoningEncryptedContent` and caps tool content at 64 KB.
- Running sessions are exported anyway (export keeps only settled
  messages) and caught up next pass.

### O10. muzzle

A server plugin `~/.config/opencode/plugins/muzzle/index.ts` (`muzzle init`):

- `tool.execute.before` for `shell` and its alias `bash` rewrites `command`
  through `muzzle wrap --json`, background calls included (they are heavy as
  often as foreground ones).
- **Permissions are judged on the user's command, not the wrapper.** The
  plugin's `permission.evaluate` hook maps a `muzzle run … -- <cmd>`
  resource back to `<cmd>` and returns the user's own rules' effect for it,
  so deny and ask survive. VERIFY in O0 with an allow, an ask and a deny
  rule.
- **Placement:** `muzzle run` records the root session id it serves (from
  `OPENCODE_SESSION_ID`, mapped to its root by the plugin) and the crew
  server instance. mu places an opencode waiter by (server instance, root
  session) against the agents row's `oc_session`, never by pane or env.

### O11. Remote opencode workers

`channelTarget` attaches a remote reader for every channel that declares
`remote: yes`, not only `hooks` (`src/channels/dispatch.ts:40-44,74-88`). A
remote opencode agent uses the remote host's mu-owned server (started there
the same way), and every create, env, prompt and log read runs
`opencode api …` through the profile's `exec` template, against that
server, with the payload as one argument capped at 96 KB before any effect
(EH-D17). A lost reply is `unknown`, resolved by the receipt lookup, never
resent.

### O12. dotfiles, org, docs

The dotfiles' attention-only plugin becomes the example of `murmur init`'s
TUI plugin; examples for the mu-crew and muzzle server plugins join it.
STANCE moves opencode into the first-class rows with its limits: no TUI
model picker authority (the session's model wins), children run without
identity, keep-driving rests on an experimental hook.

## Human decisions

- **H1.** A mu-owned opencode server per machine (recommended), or the
  user's shared service with draft 1's known holes.
- **H2.** Crew sessions in their own DB (recommended, required by H1's
  restart-recovery rule), so they do not appear in the user's `opencode`
  session list.
- **H3.** Children (native subagents) run without the worker's mu identity
  (recommended, matches the nested rule), or mu propagates it.
- **H4.** Keep-driving on an experimental hook, with the SKILL.md fallback.
- **H5.** Scope: (1) murmur state only (the TUI plugin reports
  running/idle/blocked and the turn's text; mu cannot send), (2) pane
  workers on a mu-owned server (this draft), or (3) pane-less workers over
  the API, a pane only a viewer. O0 informs the choice between 2 and 3.

## Open findings from the second refutation

Both confirmed against v2.2.7.

- **Plain `opencode serve` has no restart recovery** (high). Restart
  continuity is installed only when the server runs with a lifecycle, which
  only `--service` mode supplies (`cli/src/server-process.ts:146-160`,
  `server/src/process.ts:113-117`). A mu-owned `serve` that restarts leaves
  interrupted executions unrecovered. Options: run the crew server as
  `serve --service` with its own registration and service config (they live
  in the state and config dirs, so isolating them without moving the user's
  providers and plugins needs O0), accept no recovery (mu reports the
  sessions and the worker is reparked), or upstream a flag.
- **muzzle's permission mapping is unbuildable as written** (high). Deny
  rules are checked before `permission.evaluate` runs, and the hook gets
  only the computed effect, not the rules (`core/src/permission.ts:188-198`;
  `plugin/src/effect/permission.ts:10-19`). Both rewrite points
  (`tool.execute.before`, `shell.create.before`) run before the permission
  check, so it judges `muzzle run … -- <cmd>`. Options: rewrite only after
  permission (no such hook today: upstream), have `muzzle run` itself
  re-check the user's opencode rules for `<cmd>` (it would have to read
  opencode's config), or document that opencode shell permissions see the
  wrapper.

## History

Draft 1 (2026-11-11) used the shared service, the TUI's env upload,
`--auto`, volatile events through a TUI plugin, a per-session last-text
cache and msgId dedupe as a fence. The refutation (gpt-6.1-sol, read-only
against v2.2.7 and the crew repos) found:

| Finding | Disposition |
|---|---|
| msgId dedupe fails across cancel and revert | O3/O4: never-resend stays the rule; dedupe is a safety net |
| dedupe is not a fence | O4: `fence: none`, guarded calls refused |
| create-before-pane unjournaled | O3: `oc_session` reserved first, derived from the attempt key |
| readiness ≠ env readiness | O1, O3: mu PUTs the env synchronously; TUIs upload nothing |
| run/baseline undefined; steer ack wrong | O4: runs = settled executions; ack by inbox id |
| verb table ≠ `ChannelDelivery` | O4: per-method table, `answer` by decision, typed refusals |
| fresh broadcast not pane-targeted | O4: new session + `respawn-pane`, anchor rewritten |
| viewer TUIs overwrite env | O1: `--server` TUIs upload nothing |
| volatile SSE as sole state | O6: durable log authoritative, plugin a hint |
| last text from an earlier turn | O6: per execution interval |
| child dialogs dropped | O6: aggregated onto the root, recomputed |
