# eval harness

Black-box rig: a surface is a directory with a built mu, mu runs as a subprocess, and workers are scripted faux pis (or, in the hook-harness cases, fake claude, codex, cursor-agent and Muse Code binaries; see below). In a faux or `check` run nothing costs money; in a `run` or `matrix` with a real model only the AUT (agent under test) does, except in a live hook-harness case, where the workers are the user's real (paid) harnesses too and nothing counts their tokens (below). Imports nothing from `src/` or `extension/`.

The AUT's `pi` is a sandbox wrapper: `--version` and `--list-models` print the host pi's own output, and the real pi path, extension paths and the faux model name live under `<sandbox>/.rt/`, off the AUT's PATH. The AUT's PATH holds system dirs plus `<sandbox>/bin`; HOME is empty (a live hook-harness run keeps the caller's, below). Run from inside the host pi launcher's seatbelt (`LAUNCHER_SANDBOX_RUNTIME=seatbelt`, e.g. a pi agent's bash tool), the rig sets `LAUNCHER_INHERIT_OUTER_SEATBELT=1` for every pi it starts (`launcherEnv`): the launcher's nested `sandbox-exec` is refused there and every model fails before its first request.

- Prepare a surface: `node tools/eval/main.ts prepare 3x v3.13.3` (exports the ref into `~/.cache/mu/eval/surfaces/3x`, then `npm ci && npm run build`).
- Selftest, zero cost (faux model): `npm run build && node tools/eval/main.ts selftest [--surface <dir>]`.
- One scenario: `run` arrives with the scenario tasks. A scenario is a `Scenario` in `scenarios/<id>.ts`; `runAut(sandbox, scenario, opts)` runs it.
- Faux steps: `{calls}`, `{text}`, `{error}`, `{die}`, `{textFromLastResult}` (see `faux-steps.ts`).
- Provenance (`provenance.ts`): judges prove who did the work and in what order, not just the end state. `runs.log` lines are `<ms> <agent> <task> <action> <sha|-> <patch-id|-> <cwd>`; main's commit must be that worker's sha (or a cherry-pick with its patch-id), remote steps need a run under `<hostRoot>/home`, and order comes from ops/runs/hook timestamps.

## Hook-harness cases (E1–E7, every harness first-class)

`scenarios/e<N>_*.ts` (U24 of the [spec](../../docs/specs/2026-11-05-every-harness-first-class.md); results template and live commands in [docs/eval/every-harness.md](../../docs/eval/every-harness.md)). They are `next`-only (`families`; `check --family 3x` skips them) and carry `hookHarnesses` (the worker mix), so the sandbox gets claude, codex, cursor-agent and muse binaries and the rig's hook entries (`harness.ts`).

- **AUT harness.** `--harness pi|claude|codex|cursor-agent|muse` on `run`, `matrix` and `check`. pi runs over rpc (`runner.ts`, unchanged); the four hook harnesses run in a pane started by `mu orchestrate --cli <h> --name aut` (cursor-agent and muse with the trust and approval flags of `AUT_FLAGS` in `harness.ts`, since mu's spawn presets are a worker's), prompted by `mu agent send` (claude and cursor-agent once their session started, codex and muse once no trust dialog is up), settled by murmur's view of the pane (`runner-pane.ts`), whose scrollback is read for a sandbox refusal (`sandboxRefusal`: noted `environment: ...`, a failure of the rig's environment, not the AUT's). Their mu calls are the AUT's in `mu-calls.log` (agent `-`). A `replacement` case (E4) crashes the AUT (a fake one on its script's `{die}`, a live one when `crashWhen` holds) and starts `aut-2` with the replacement prompt; the faux pi AUT's phase 2 runs the steps after the `{die}` (`EVAL_FAUX_PHASE=2`).
- **Worker mixes and the plan (`mix.ts`).** E1, E3, E4 and E6 take `--workers <h1>,<h2>` (claude, codex, cursor-agent, muse) on `run`, `matrix` and `check`: `bindScenario` binds a case to its AUT and mix (`Scenario.bind`), so its prompt, title and judge name those harnesses; the scripts read them as `$EVAL_W1`, `$EVAL_W2`; the result row records `workers`. A Muse AUT's prompts end with `MUSE_DRIVE` (it has no mu Stop hook, D7); E2 takes a cursor-agent or Muse AUT's model family from `--model` only (their hooks name no vendor) and, when it is unknown, tells the AUT plainly to use a claude refuter (`bind` gets the model); a refuter of unknown family never counts. `EVERY_HARNESS_PLAN` is the sampled live plan (claude, codex, pi: E1-E7; cursor-agent and Muse: four cases each with chosen mixes), and `check --plan [--harness h]...` proves its rows.
- **Hooks.** The rig writes the observer hook (`hook-observer.ts`, one JSON line per event into `<workers>/hooks.log`), murmur's, mu's Stop entry and muzzle's into project files committed in the sandbox repo (`.claude/settings.json`, `.cursor/hooks.json`, `.muse/hooks.json`) and codex's into its home. Every entry runs the worktree build by absolute path: the surface's mu, `EVAL_MURMUR` (required), `EVAL_MUZZLE` (optional). The sandbox's `mu`, `murmur` and `muzzle` shims drop harness hook calls, which only a user's own entries make, and pin the sandbox's DB, state, sync dir and tmux server whatever the caller's env says (`isolation.ts`; a live sandbox also re-pins after the user's zsh startup files and through claude's `CLAUDE_ENV_FILE`, and a watch on the user's real sync dir, DB, murmur and muzzle state marks a run destructive when a new segment appears in the sync dir and notes every other change, reporting even when the run is interrupted).
- **Fake harnesses (`check`).** `fake-harness.ts` reads its pane like the real harness (bracketed paste, `C-u`, Escape; claude puts an interrupted prompt back in the line), fires the real one's events from the real one's config files with the U0 payload keys (`fake-payloads.ts`; Muse's hooks get its cleared environment), and runs faux steps: a worker `<workers>/<agent>[.<n>].json` or `default.json`, the AUT the script named in `<workers>/aut-script`. A Stop block continues the turn with its reason.
- **Live runs** keep the caller's HOME, env and auth for the AUT and its workers and run the user's own harness binaries; `docs/eval/every-harness.md` lists exactly what the rig changes, codex's global hooks.json and which mu skill each AUT reads included (`EVAL_CODEX_HOOKS=global|codex-home`). Before the AUT starts, a live run with real workers pre-trusts the sandbox for claude and (with `codex-home`) codex: it starts each once in a pane, answers its trust dialogs and quits before any prompt (`pretrust.ts`; a step it cannot confirm becomes a run note). `--fake-workers` keeps fake workers beside a real AUT; `EVAL_AUT_COMMAND` replaces the AUT pane's command. **No token bound:** a pane AUT reports zero usage and real workers are never counted, so a scenario's `tokenCap` and matrix's `--budget-tokens` do not limit these runs; only each run's timeout does.
- **`check` without `EVAL_MURMUR`** skips each hook-harness case with one line and runs the rest.
- **Judges** read the ops log, `runs.log`, `hooks.log` (`harness-observe.ts`), git and the main-commit log, through the shared rules of `harness-cases.ts` (`taskProof`: the worker's own commit, its place, its harness by spawn and by hooks, closed after its report). `test/eval/harness-judges.test.ts` pins each case's golden and bads on synthetic end states. A failed AUT mu call is a note in these cases, never a wrong entry, for every AUT harness alike (`caseVerdict`, `failedMuCalls: "notes"` in `score.ts`): the notes come from the shim's `mu-calls.log` (agent `-`), which records a pi, claude and codex AUT the same way, while only pi has tool-call records; and a refused call the AUT recovered from is no wrong effect. The older scenarios keep counting pi's failed calls as wrong unless `expectFail` allows them.

## Surface family and candidate scenario roots

A `--surface <spec>` is `<dir|name>[:<3x|next>[:<scenario-root>]]`. A bare name is a built surface under `~/.cache/mu/eval/surfaces`; `check`, `run` and `matrix` all resolve it the same way. Family and root belong to the surface, so one matrix can pair a baseline with candidates. `--family` and `--scenario-root` only fill specs that leave them out; the defaults are `3x` and `tools/eval/scenarios`. Results and run logs key on a surface id, `<name>:<family>:<hash of dir+root>`, so one built dir under two specs stays two report rows; `matrix` refuses the same spec twice.

- The family is exactly `3x` or `next`. The sandbox sets `EVAL_SURFACE_FAMILY` from it, and `writeWorkerDriver` reads it: workers close with the verb on `3x` and print the `CLOSE:` block on `next` (an explicit `closeMode` wins). The judges do not change with the family.
- A scenario root holds `<id>.golden.<family>.json`, `<id>.bad.<family>.json`, `<id>.bad-<x>.<family>.json`, and optional `<id>.ts` overrides (which import `../../fixtures.ts`). An id missing from the root falls back to the default scenario. It must not be inside the surfaces cache (`prepare` deletes there). Keep candidate roots under `tools/eval/candidates/<decision>-<a|b|c>/` (gitignored).

```bash
R=tools/eval/candidates/dec-a
node tools/eval/main.ts check --surface "$PWD" --scenarios _smoke --include-underscore          # 3x, default root
node tools/eval/main.ts check --surface dec-a --family next --scenario-root $R                 # cached name
node tools/eval/main.ts matrix --surface 3x --surface "dec-a:next:$R" \
  --model haiku-5-5 --model sonnet-5-5 --scenarios delegate_saturation --out results.jsonl
```

## Pending `next` scenarios

A scenario whose `next` golden needs a verb that is not merged yet (the unified `mu wait`, delegate waves through it, settle) keeps its scripts as `<id>.golden.next.pending.json` and `<id>.bad[-name].next.pending.json`, written against the planned README surface, and is listed in `PENDING_NEXT` (`check-rules.ts`). `check --family next` prints `<id> pending: skipped` and runs nothing for it; `--family 3x` is never affected (its `.3x.json` proof stays). Today: none. `v_wait_surface` shipped `mu wait` and flipped `wait_interrupted`, `wait_mixed_refs`, `wait_wave_six` and `wait_wave_starvation` (the judges' native guarantees: a wait that prints the snapshot, one wait over task and agent refs, a per-wave tally inside the wait).

The unit that ships the verb flips its scenarios in its own commit, as its tier-1 gate: for each `<id>`, `git mv` every `*.next.pending.json` to `*.next.json`, delete the id from `PENDING_NEXT`, fix any spelling the shipped verb settled differently (the pending scripts use `mu wait [task:<id>|agent:<name>] --all --wave <w> --until-text <re> --json`), then `check --surface <build> --family next --scenarios <ids>` must pass every golden and flag every bad. `test/eval/check.test.ts` fails if a pending file has no listed id, a listed id has no golden and three distinct bads, or a live `.next.json` exists beside a pending one. The holdouts (`worker_dies`, `wait_receipt_race`, `wrong_id`, `single_channel_host`) are never tuned or flipped here.

## Native guarantees and N/A

A guarantee only a candidate can give (mid-wait delivery, a snapshot printed by the wait itself, one wait verb, receipts) goes through `lifecycle.native()`. Missed on the 3x family it becomes `Verdict.na` (never a pass, never a wrong entry); missed on `next` it is wrong. `score.verdict` turns `na` into `N/A baseline 3.x:` notes plus a `manual workaround` note, `check` marks the golden `(manual workaround: n N/A native)`, and `report` shows an N/A column plus a legend line per scenario. A Completed on such a row is a manual workaround, not the guarantee.

Fault injectors for waiting scenarios live in the worker driver, keyed by task: `errorOnce` (API outage, task stays IN_PROGRESS), `dieOnce` (the pane dies), `loseOnce` (the prompt is delivered and silently dropped: the worker does nothing, runs.log records `lost`). A judge reads the injected faults from runs.log, never from the AUT's words. `ssh-shim` logs the opener's `TMUX_PANE` in `sessions.log`, so a judge can tell a pane's ssh session from an AUT tool call's.

## Judges assert effects, not spellings

A judge never matches a verb, a flag, a hint string or an exit code that a surface changes (`task note` vs `task note -m`, `task wait` vs `mu wait`, a timeout's exit 5 vs `ok:true` with `timedOut`). It asserts what mu and the workers observably did, through `observe.ts`:

- **mu-call record.** The sandbox's `mu` shim appends `<start> <end> <exit> <agent|-> <pid> <argv>` to `<workers>/mu-calls.log` for every invocation (`-` = the AUT) and tees the AUT's own stdout to `<workers>/mu-out/<pid>`, before any pipe the AUT adds. A _wait_ is a mu call that blocked (`WAIT_MS`), whatever its verb; _a timeout_ is `timedOut` observed in that call's own output, whatever its exit code; _a task observed CLOSED_ is a successful call whose own output shows it. The shim changes neither output nor exit status.
- **Ops log and DB.** Who owned a task, who closed it (`task.close` actor), a note's text and kind (`task.note` intent), a raw SQL write (`sql.*` intent), a teardown (`workstream.teardown`), a closed agent (`agent.close`). `verdictFx` adds the effect-based destructive entries to EVERY judge (`test/eval/judges-effects.test.ts` runs every judge against a sandbox holding a raw write and fails one whose verdict lacks it): ops, `lostWork` (a worker commit on no ref and not on main, which any premature discard leaves behind), and `localWrites` (a raw `mu sql` write to a machine-local table such as `agents` leaves no op: the shim fingerprints those tables around each AUT call into `<workers>/mu-local.log`; a successful call that changed one while its own output reports a SQL write result, or whose argv holds a write statement (`... RETURNING` prints rows), is a hand write).
- **Prompt log.** The faux worker driver writes every prompt its model receives to `<workers>/prompts.log` (`<ms> <agent> <session-messages> <text>`) and every delegate answer it serves to `answers.log`. A reset is a prompt that arrived into a fresh session; a resend is a second work prompt; a delivery is the AUT mu call whose argv carries the prompt text, however it was spelled (`send`, `spawn --send`, a function).
- **Family options only.** A guarantee only a candidate gives goes through `lifecycle.native()` (3x: N/A, next: wrong); a spelled regex is never a family switch.

Every scenario with more than one valid spelling ships extra goldens, `<id>.golden-<name>.3x.json` (the same job through a variable, a function, another verb): `check` runs them all and each must be clean. Prompts that need a mu behaviour name the effect, not the 3.x command.

## Cold-guess probe

`node tools/eval/main.ts cold-guess run|check|report` (`cold-guess.ts`, `cold-intents.ts`, `cold-report.ts`). Not a scenario: a one-shot reading test of a surface. The model gets only that build's help bundle (`mu --help` plus `mu <group> --help` of every group with subcommands, the same depth on every surface; `cold-help.ts`; no skill, no tools: `pi -p --no-tools`, empty HOME) and one short intent, and answers with a single command; the command runs in a fresh seeded sandbox and the intent's judge reads the state and the command's own output, never its spelling (`hit` also needs no stray op beyond what the intent allows). `check` proves every judge with a golden, a plausible bad and a no-op per intent (zero model cost; run it on each family before a `run`). `run` appends one row per guess to a JSONL and skips rows already in it (`--out` is resumable); `report` renders the tables of `docs/eval/cold-guess.md`. `--surface [label=]<spec>` can repeat; the label keys the rows. Requests are neutral: `cold-help.ts` lints every request against the command, subcommand and flag names of every surface in the run (`run` refuses to start on a leak; a quoted payload is exempt via `payload`). Each intent has a `role`: `headline` (pre-registered; counted in the headline, with per-intent wins/losses/ties at a 2-hit gap) or `control` (added to separate one cause of a miss; reported apart). An intent only some families can express lists them in `families` (delegates exist only on `next`).

## Exposure and tournament statistics (hill-r2)

`exposure.ts` and `stats.ts` are the scoring core of the hill-r2 tournament ([spec](../../docs/specs/2026-11-07-hill-r2-tournament.md) §4, §5). Both are pure.

- **Exposure** (`probeExposure`, `r4Exposure`) says whether a row saw a variant's changed text (its derived markers; context markers on base rows, through `baseSpec`) or ran into its changed behaviour (a call matching `changedCalls` or using a `newNames` flag or verb). A probe has two views. `winExposed` is fixed before the answer: markers in the prompt, or a changed call in the lead-in. It is the only view `winClusters` reads. `scanExposed` adds the answer's own changed calls, for scans and attribution only. Selecting win clusters by what the answer did would pick clusters by outcome and inflate false wins.
- **Attribution** (`attribute`, `attributeProbe`, `destructiveOutcomes`): a destructive entry counts against a variant only when it ran in the exposing call itself or in the next assistant message. Placement comes from `ToolCall.turn`/`idx` (filled by `MetricsCollector`) and from `Verdict.destructiveFx` and `Verdict.muCalls` (built by `verdictFx`). An unplaced entry or exposure goes to a review stop.
- **Statistics:** one-sided Fisher exact and its exact power, MDE, Holm, the one-sided continuity-corrected stratified CMH test, one-way ANOVA ICC (per model and pooled across models), DEFF and Kish scaling, and the n-plan solver. `test/eval/stats.test.ts` pins them to the spec's §4.2 power rows, the R reference for CMH (`UCBAdmissions`) and a Monte Carlo null rate.

## Next-step probe

`node tools/eval/main.ts nextstep run|check|lint|selftest|report` (`nextstep.ts`, `nextstep-exec.ts`, `nextstep-cases.ts`, `nextstep-report.ts`; spec [docs/specs/2026-11-07-hill-r2-tournament.md](../../docs/specs/2026-11-07-hill-r2-tournament.md) §1). A one-shot reading test in the middle of a session. Per row the rig seeds a fresh sandbox, runs the case's lead-in as the orchestrator (`PI_SESSION_ID=nextstep-orch`, each step as `{ cmd } 2>&1` under the case's shell, bash or zsh) and renders what it printed, with pi's `Command exited with code N` / `Command timed out after S seconds` lines. The model gets that transcript, a goal and its arm (`none`, `skill`, `recipe:<name>`, read from the surface under test), and answers with one to three commands in ```` ```sh ```` blocks (more than three runs nothing). The commands run in the same sandbox as the orchestrator; `<workers>/go` is touched just before the first one, so a gated worker's delay starts at the answer.

- **Printed** (`shown`, for nonce markers): one answer command holds a mu call whose own output (`mu-out`) has the marker, a line of that command's own output holding the marker also occurs in that call's output (raw or as a decoded JSON string, so `jq -r` counts and `sed s/N1-/N2-/` does not), and no answer command's text holds the marker once quotes, backslashes and whitespace are deleted. `shownLine` is the same for a line that satisfies a predicate (a state line), verbatim.
- **Timed cases** (the goal state arrives after the answer starts) also need no idle command and no polling one (`pollingCalls`). A command of 3 s or more is idle when the union of its mu calls' intervals covers less than half of it, or leaves 3 s or more outside mu: two overlapping background waits count once.
- **Hit** = the judge's effect, no stray op, no kill unless the case allows it, no destructive entry, and the timed rule. Rows record destructive entries only; exposure and attribution are `exposure.ts`'s.
- `check` proves every case per lead-in variant at zero model cost: the golden and each `alt` hit; the bad, `true`, each `lucky` spelling or forgery and the `sleep` row miss. `selftest` drives `runNext` end to end with the scripted models `evalfaux/golden` and `evalfaux/bad` (`askModel` answers them from the case, no pi starts), checks the stored prompts, resumption and the report. `lint` fails a goal that names a base command, subcommand or flag, a lead-in verb outside `leadInVerbs`, a last lead-in step that is not mu, and a headline case without ten paraphrases (a guard needs six); a name only a variant has is a nameCue. `run` refuses to start on a lint failure, appends rows to `--out` and skips rows already there; prompts go to `prompts/<sha>.txt` beside it. `report` prints raw counts per round, surface, case, arm and model (no tests: `tournament report` has them). On macOS run with `TMPDIR=/tmp`: the default temp dir makes the sandbox's tmux socket path too long.
